# TODO Rules

## Purpose

本文档定义根目录 `TODO.md` 的任务类型、人工确认边界、内容格式、执行许可和收口规则。

`TODO.md` 是未关闭任务面板，不是方案正文、执行日志或完成历史。

## Task States

`TODO.md` 固定包含三类区域：

- `当前任务项`：已经确认，可以执行的有界任务。
- `待审阅任务项`：已经形成可执行描述，但仍需人工确认范围或许可。
- `待讨论项`：尚需产品或技术决策，不能直接实现。

只有用户明确确认，或用户直接要求执行某个明确范围的任务，才能将任务视为当前任务。Agent 不得把待讨论项自行解释为实现许可。

用户直接委派的一次性明确任务可以不先登记到 `TODO.md`；只有已经登记的任务才适用 TODO 的移动、删除和收窄规则。

## Item Format

执行任务至少包含：

```markdown
- [ ] `范围对象`：任务标题
    - 依据文档：`docs/.../XXX.md`
    - 确认依据：确认日期、Issue、讨论或 PR 链接
    - 处理动作：一句话说明要完成什么
    - 验收点：可以观察或执行检查的结果
```

待讨论项至少包含：

```markdown
- [ ] 需要决定的问题
    - 决策要求：需要人工确认的具体选择或边界
    - 影响范围：会被该决定影响的产品或工程领域
```

规则：

- 一个任务只表达一个主要目标。
- 范围对象必须能稳定定位到领域、模块、文件或流程。
- 依据文档必须是当前有效的治理、需求、接口、设计或 RUNBOOK。
- 从待审阅任务移入当前任务时，应补充可以追溯的确认依据。
- 验收点必须可检查，不能只写“完成优化”“体验良好”等主观结果。
- 长篇背景、方案比较和研究过程应放在对应文档中，TODO 只保留链接和动作。
- 低置信度观察不得直接进入当前任务项。

## Discussion To Execution

待讨论项形成结论后：

1. 将确认的产品行为写入 `10-requirements/`，或将稳定工程规则写入 `00-governance/`。
2. 如果仍需要实现，新增一个或多个有明确范围和验收点的待审阅任务。
3. 获得人工确认后，移入当前任务项执行。
4. 删除已经解决的待讨论项，不在 TODO 中保存决策历史。

对于用户直接要求完成的明确任务，可以直接执行，但仍必须遵守现有需求、架构和权限边界。

## Closure Rules

- 完成整项：在真正完成该任务的 commit 中删除对应 TODO。
- 只完成部分：把 TODO 收窄为准确的剩余范围。
- 发现拆分错误：停止扩张范围，重写为正确的待审阅或待讨论项。
- 任务产生长期结论：在关闭前迁移到对应治理、需求、接口、设计、readiness 或 operations 文档。
- 临时 RUNBOOK 完成后：迁移长期结论和验证证据，再删除 RUNBOOK 及残留引用。

未创建 commit 时可以在工作区同步更新 TODO，但不得把尚未完成的任务标记为关闭。

## Verification Check

任务收口前至少检查：

- 目标行为是否达到可运行、可观察或可审阅状态。
- 是否覆盖关键成功路径、失败路径和权限边界。
- 是否需要新增或更新自动化测试。
- 是否需要同步需求、接口、设计、操作或文档路由。
- 是否记录了不能执行或未通过的验证，而不是把它描述成成功。
- 工作区是否混入其他不相关修改。

验证脚本如创建临时数据、进程、目录或环境变量，应遵循：

1. `Prepare`
2. `Execute`
3. `Assert`
4. `Restore`

失败路径也必须执行 `Restore`。

## Commit And PR Boundary

- Commit 的授权、粒度、消息、验证和历史安全以 `docs/00-governance/COMMIT-RULES.md` 为准。
- PR 表达阶段性交付边界，具体规则以 `docs/00-governance/PR-RULES.md` 和 `.github/pull_request_template.md` 为准。
- 不得把未验证、未收口或范围不明的工作描述为可交付状态。
