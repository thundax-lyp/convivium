# Test Rules

## Purpose And Scope

本文规定 Convivium 测试的有效性、保留价值和维护要求，适用于新增、修改、评审及精简测试。目标是在满足必要验证要求的前提下，减少无效断言、重复代码和不合理的执行成本。

行为依据的优先级遵循 [Document Rules](./DOCUMENT-RULES.md)。测试运行、证据复用、资源清理和交付要求遵循 [Engineering Rules](./ENGINEERING-RULES.md#validation-and-evidence)。本文定义判断标准；[TDD](../../.agents/skills/test-driven-development/SKILL.md) 和 [Testcase Review](../../.agents/skills/testcase-review/SKILL.md) 分别说明开发与审查方法，触发方式由根 `AGENTS.md` 和各 Skill 配置维护。

## Terms

| 术语 | 本文含义 |
| --- | --- |
| 行为要求 | 系统在规定条件下应满足的输入输出、状态、副作用或交互契约 |
| 测试场景 | 一组前置条件、输入或事件及其预期结果；同一行为要求可以需要多个场景 |
| 测试用例（case） | 可独立执行并报告结果的验证单元；参数化测试中的每个数据行也代表一个 case |
| 断言依据（oracle） | 判断实际结果是否正确的标准及来源，包括确定值、性质、关系或可信参考结果 |
| 错误识别能力 | 测试在目标错误存在时失败、在满足行为要求时通过的能力；讨论时需指明具体错误 |
| 增量价值 | 相比现有测试，新增的错误识别能力，或明确改善的反馈速度、失败定位与验证成本 |
| 测试资产 | 长期维护的 case、断言、fixture、替身、helper 和执行配置；临时调试产物不自动进入其中 |

“覆盖同一规则”不等于“能够识别同一错误”，“代码重复”不等于“场景重复”。不要求为这些概念建立台账或评分。

## No Tests For Tests

禁止对测试进行测试：不得为测试用例、断言、fixture、mock/fake、测试 helper、测试数据生成器或测试专用脚本再编写测试，包括检查测试源码包含某个断言、验证 mock 按预设返回值工作，或为测试工具另建单元测试。

测试辅助代码有问题时，直接修正、简化或移除，并运行使用它的生产行为测试；不能增加一层测试来维持复杂的测试设施，也不能把测试专用代码搬进生产目录来绕过本条。

测试设施复杂到需要独立测试才能建立信心时，应减少其职责、改用固定数据或现成设施，并通过使用它的生产行为测试验证。

直接运行测试、审查测试代码，以及用生产代码的修复前版本或定向生产故障确认回归识别能力，仍是必要的验证方式；这些操作不新增以测试资产为被测对象的用例。

## Behavior And Oracle

永久行为测试需同时满足以下条件：

1. **预期有依据。** 对应有效需求、领域不变量、接口契约、已确认缺陷或明确的兼容承诺。具体风险可以证明为什么需要测试，但不能单独决定正确答案。测试名称、少量必要注释或已有文档应足以解释依据，无须给每个断言增加编号。
2. **目标错误可描述。** 能指出一个违反该要求的具体错误，例如错用接收方、漏掉状态写入或接受过期请求；不要求错误曾在生产发生，也不因源码中存在一个分支就假定需要单独测试。
3. **断言能够区分。** 测试确实执行目标行为，断言可以识别所述错误。仅能感知无契约意义的源码、私有结构或措辞变化，不满足这一条件。

预期不能仅由正确性未知的当前实现推导，也不能由正在被检验的逻辑同时计算 actual 和 expected。手写 literal 并不自动具有独立依据。可以使用手工核对的数据、独立参考实现、性质测试或关系断言，但必须解释为什么该参考或性质成立；共享与目标错误无关的构造工具不因此被一律禁止。

characterization test 可以记录既有行为，用于有明确兼容目的的迁移或重构；其证据只支持“保持已记录行为”。现状与正式需求冲突时应报告冲突，不能把现状直接提升为正确规范。

## Boundary And Doubles

测试结论以实际执行和断言的范围为限。隔离测试可以证明调用方如何处理某个依赖响应；要证明真实依赖、事务、装载或跨组件协议成立，需相应的真实组合证据。具体 DSH 验证边界仍遵循 Engineering Rules。

替身可以用于隔离依赖、控制时间和随机性、构造难以稳定触发的故障，或观察契约要求的交互。使用替身时必须保持以下边界：

- 被宣称验证的行为没有被替身直接提供。例如可以模拟 repository 写失败来验证调用方恢复，但不能 mock 掉恢复逻辑再宣称恢复已验证。
- 模拟的成功、失败、返回数据和副作用符合当前场景的依赖契约。刻意输入不合法数据用于检验信任边界时，应明确这是负向输入，不能伪装成正常数据。
- 接收方、参数、次数或顺序属于行为要求时，可以通过 spy/mock 断言；没有契约意义的内部调用不因可观测就值得冻结。
- fixture 满足目标边界所需的字段和语义；不靠类型强转掩盖不完整的正常数据，也不要求复制无关可选字段。

依赖替身过于复杂时，应比较更窄的测试入口或真实组件组合。测试 helper 留在测试代码；生产接口或清理方法是否合理，由真实职责和资源所有权决定。

本项目对接线、编码和配置的责任可以通过执行结果验证，不重复证明框架的通用机制。静态架构、格式或源码约束检查可以验证其声明的结构规则，但不能冒充运行行为证据。Agent 指令的结构检查同样不能证明使用效果。

## Asset Lifecycle

临时 probe、print、脚本和探索测试可用于诊断。长期保留前需满足行为测试有效性要求，并通过下节的增量价值与成本判断；其余可吸收到已有测试或清理本次临时产物。

新增测试先比较已有保护。增强现有用例即可覆盖目标错误时，优先增强；新场景或不同验证边界使独立 case 更清楚时，可以新增。普通 getter、无逻辑委托和人类说明文档不因其存在而需要专门行为测试。

行为要求改变时，更新受影响预期并保留仍成立的场景。行为保持的重构通常只需运行既有测试；测试入口变化可以需要机械调整，实际保护缺口也可以补齐，但不得按新实现结构重新生成整套断言。

## Portfolio And Cost

保留价值由测试提供的证据及其成本共同决定。先满足明确验收要求、项目必需检查和必须保持的不变量，再在可行方案间比较：

- 能识别哪些错误，触发条件是否可达，错误后果如何。
- 比现有测试多提供什么证据，或能否更快、更明确地定位同一错误。
- 需要维护多少代码、数据、依赖和修改点；运行耗时、资源、外部调用及不稳定成本如何。

减少重复代码本身是收益，即使执行时间不变。代码行数、case 数、coverage 或 mutation score 只能提供调查线索，不能单独决定增删。无法量化的风险和成本用具体条件说明，不编造概率、分数或加速幅度。

### Merge And Code Weight

| 操作 | 成立条件 | 必须保留的内容 |
| --- | --- | --- |
| 参数化或共享 setup | 操作和断言结构相同，差异可由清楚的数据表达 | 必要输入、预期、隔离和每例失败定位；通常不减少执行次数 |
| 合并断言到一个 case | 多个断言共同验证一次行为的结果 | 所有互补结果；独立场景仍独立执行 |
| 删除重复场景或断言 | 其他保留测试能识别同样的相关错误，且被删部分没有值得保留的定位或反馈优势 | 指明承接保护的 case 与断言 |
| 提取或移除 helper | 改动降低整体重复、理解或维护成本 | 场景意图和必要的执行条件仍容易追踪 |

相同高层要求下，不同输入可能经过不同校验或触发不同错误，不能仅凭结果相同减少场景。减少代码也不能通过把独立场景串成依赖共享状态的大测试实现。

共享 fixture、工厂或跨文件 helper 并非问题本身；比较其减少的重复与新增的间接理解成本。共享可变资源时必须保持 case 隔离及失败后的清理。

### Execution And Maintenance Cost

优先改善重复环境初始化、无关大数据、固定等待、重复外部调用和与内部结构耦合的断言。缩小数据量前核对其是否恰好用于分页、容量或性能边界；替换真实组件前核对目标错误是否仍可被识别。

结构性简化建议可以基于代码分析；运行耗时高或替代方案更快的结论需有相关运行数据。缺少数据时将性能结论标为待验证，不默认为成本评估新增基准测试。

确定性时钟、条件同步和故障注入可降低运行成本，但不能据此宣称真实时序或外部协议已验证。重复执行需服务于发生变化的代码、已知不稳定性或尚未解决的证据缺口。

偶发失败需区分产品竞态与测试隔离/环境问题。增加重试、跳过或删除不能被描述为修复了原失败；确需调整执行策略时，说明原因、剩余风险及证据影响。

## Review And Disposition

处置需对应具体证据，区分以下情况：

- **增强或改写**：行为依据成立，但当前输入、断言或替身不能识别目标错误。
- **合并或简化**：必要场景仍成立，可减少重复代码、无关数据、间接封装或执行开销。
- **替代**：更低成本的测试或已有验证能承担所需证据，明确替代前后的范围。
- **删除**：保护已被承接、对应行为已退役，或无效断言移除后没有留下必须补齐的验证缺口。
- **调整非必需验证**：测试有独有证据但成本不相称，先比较简化、替代或降低运行频率；仍建议取消时，应说明丢失的证据、剩余风险及允许该取舍的依据。这不等于证明原测试重复或无效，不能自行降低明确验收要求。

来源不明或重复关系未确认时，先调查，不能把未知写成确定删除建议。缺少同一错误的动态复现不必阻止所有判断，但必须区分静态论证和运行证据。

合并或删除建议需指出原用例保护的具体错误，以及保留用例的输入和断言如何继续识别它；存在保护损失时，说明损失和处置依据。不能只用“已有覆盖”作为理由，无须为未调整的用例建立台账。

## Feedback And Evidence

新写或修改的测试需直接运行；对缺陷回归，应尽可能确认修复前失败、修复后通过，并核对两次结果确实来自目标缺陷。必要时可用隔离副本中的定向生产故障确认错误识别能力，不另写测试去验证断言；是否需要额外运行取决于风险与已有证据。

通过只说明已执行断言在该版本和环境下成立。编译/环境错误不能单独证明行为测试有效，RED/GREEN 也不证明预期依据正确或需求已完整覆盖。

测试精简需对照前后输入、断言及验证边界，并运行受影响检查；全绿或 coverage 不变不足以证明未丢失必要保护。命令、结果与未验证范围按 Engineering Rules 报告。TDD 的开发顺序由对应 Skill 说明。

## Test Naming

测试文件和 `describe` 按稳定的业务对象、业务能力或工程边界命名；`it`/`test` 说明触发条件和可观察结果。不得按临时任务、RUNBOOK、审计报告、阶段或 finding 编号组织长期测试；回归应归入对应对象已有测试。需求编号可写在必要的依据注释或 readiness 中，不替代测试名称。纯工程组件沿用其稳定对象名称（例如 Storage Domain、outbox、plugin lifecycle）。参数化 case 的名称应能识别输入情景，失败时不只显示无语义行号。
