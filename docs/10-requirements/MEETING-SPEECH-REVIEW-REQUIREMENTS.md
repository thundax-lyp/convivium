## Purpose

围绕用户目标建立求解路径，以证据和分析不断修订路径，形成可执行的一致性方案。通过 Manager 组织研究、整合阶段成果及审核边界，避免偏题发言与 Agent 执行自述在公共上下文中反复传播。发言秩序与审核通过本身不是会议成果。

## Scope And Non-goals

适用于 Participant 发言及关联证据的提交、边界审核、退回修改、正式发布与后续上下文使用，以及证据保存、访问和独立核验。Manager 负责边界判断，Runtime 负责授权、状态和发布流程。

不由 Manager 判断观点是否与自己一致，不以边界审核代替事实核验、成果审核或 Captain 的决策接受。不删改历史正式原文，不把既有发言来源和独立性审计信息删除，不采用关键词过滤代替语义审核。

## Functional Requirements

1. Transcript 是会议公共内容，按议题组织核心观点与关键证据；身份只作为来源追溯信息，不作为观点正确性的依据，不在正文重复 Agent 的身份、权限或执行过程。
2. Participant 依据已公开 Transcript 搜集和核对证据，提出自己的观点，回应前序内容。引用须可追溯；证据的来源、假设及待验证状态应可区分，公开不等于已证实。
3. Manager 根据会议目标明确当前议题的范围、边界和预期贡献，不得擅自改变用户目标。审核采用明确的边界，不以临时个人偏好要求参会者服从结论。
4. Participant 的新发言先成为待审提交。审核通过前不得进入正式 Transcript、其他 Participant 的讨论上下文或成为完成、决策与后续事实的依据。为处理该提交而授权的证据审核员可访问核验所需的材料及主张，访问边界见下文公共证据区要求，不因此获得公开发布权。
5. Manager 对每次待审发言进行边界审核。通过后由 Runtime 发布原提交的确切版本；Manager 不得代写、悄悄改写或以自己的观点替换提交。
6. 越界时提示具体段落、所违反的边界和修改方向，退回原 Participant 修改重提。退回内容与反馈只向处理该提交所需的身份开放，不作为公共议题正文传播。
7. 反对方案、质疑前提、指出关键风险及解释必要背景均可属于合法贡献；不能因不同意 Manager 或多数意见而判定越界。运行限制实际阻塞会议时允许简述影响及所需动作。
8. 审核必须绑定具体提交版本及其适用边界。修改后的版本需要重新审核，旧批准不能发布新内容；过期或重复操作不得错发、重发或改变已生效结果。
9. 审核等待与退回重提必须有明确上限。Manager 不可用、审核超时或无法在上限内收敛时，向召集人报告原因与待处理项，不自动放行未审内容，也不无限循环。
10. 审核过程保留必要追溯，但不混入正式议题正文。用户应能区分待审、退回、已正式发布与等待召集人处理的状态。

### Collaborative Problem Solving

会议按以下主线推进，允许因新证据返回前序步骤修订：

**明确目标 → 建立候选路径 → 找出关键未知 → 搜集证据 → 分析与比较 → 修订路径 → 形成一致性方案。**

- Manager 首先组织求解路径、识别证据缺口和整合阶段成果；边界审核辅助这些职责，不以审核发言数量衡量进展。
- Participant 围绕路径承担研究与分析任务，提交可整合的观点、证据、推导及修订建议，不为表达立场或回应每条消息而参与。
- 证据审核员说明证据能支持哪些选择、仍缺什么以及适用限制，帮助修订方案；寻找反例是核验手段，不以反驳数量为目标。
- Transcript 应体现路径、证据、分析与方案如何逐步形成。按人排列的正式发言原文保留为追溯材料，不以逐人复述替代公共成果组织；阶段归纳须保留来源及分歧，不覆盖原文。
- Agent 参与下一步主要由待解决问题、待补足证据或需要修订的路径驱动。Transcript 变化是发现相关工作的信号，不是必须发言的理由；已有申请、审核及并发机制均服务于求解任务。
- 一致性方案应满足目标一致、各部分相容、关键选择有证据支持、执行路径明确，剩余假设与风险已显式处理。不要求全体成员口头赞同；保留未消除分歧并说明其是否影响方案成立，不得通过隐藏异议制造共识。

### Common Argument Format

2026-09-14 用户确认各 Agent 的公开论证使用同一格式，以便比较、审核和整合；身份、授权与调度信息仍不属于论证正文。该格式用于论证贡献，不要求发言申请、调度通知或权限错误也伪装成论证。

| 项目 | 提交内容 |
| --- | --- |
| 主张 | 认为应该怎样做，或应如何修改已有判断，并关联待解决问题或候选路径。 |
| 证据 | 支持该主张的数据、来源或实验，保留可追溯引用；没有支持证据时明确写明尚无证据。 |
| 推断 | 解释证据为何支持主张，区分直接观察与解释，列明推导所需假设。 |
| 反证条件 | 说明出现什么可观察结果会修改判断，不以无法检验的表态替代。 |
| 不确定性 | 列出未验证部分、适用限制及尚缺的验证。 |

五项均需明确交代，不得为了填满格式编造证据、实验结果或确定性。证据质疑也使用同一格式：主张可以是某条证据不足以支撑某个选择，说明质疑依据、推导缺口和什么核验结果会消除质疑；不强迫质疑者另造一个替代产品方案。

例如，“微服务更适合我们”只有主张；若实际压测发现瓶颈集中于一个模块，拆出后吞吐量提高，则应提供相应压测依据，说明负载可比等假设，同时标注部署成本尚未测量，并给出会改变该选择的可观察条件。此例说明论证结构，不是本项目已经执行的实验或架构决定。

### Evidence Source Independence

- 多个 Agent 引用同一篇文章，只算一个证据来源，不能因引用者或重复次数增加而算作多次独立验证。
- 证据来源、对来源的引用次数与实际独立核验应区分。不同链接、转述或转载同一原始材料不能仅凭链接不同就认定独立；明确共享来源或数据的依赖关系，无法判断时标记独立性未核实。
- 多人阅读同一材料可以产生不同分析，但不自动增加独立证据。声称独立验证时须说明实际执行方式、材料或数据、观察结果，以及与既有验证的依赖关系；仅有不同 Agent 身份不足以成立。
- 证据审核员检查来源独立性和重复引用；Manager 整合方案时不得把重复引用或多人赞同当作证据增强。不预设自动置信度分数或以来源数量替代证据质量。

### Evidence Submission And Shared Access

Participant 提交观点及证据时，必须同时将核验所需材料保存或关联到会议公共证据区，并引用具体证据版本。公共证据区是会议内受控共享能力，不指定目录、数据库或存储介质；仅有“已查阅”“测试通过”、私有 Session 内容、本机临时路径或审核人无权访问的链接，不构成可供核验的材料。

- 提交时，Manager 及获授权处理该提交的证据审核员能够访问相同版本的材料与必要主张上下文；边界审核通过后，材料才可向全体参会者公开。待审及退回附件不得绕过正文准入提前传播；已公开的旧证据不因被新待审稿引用而撤回。
- 材料无法保存、访问或缺少必要上下文时，明确标记材料不可访问或证据不完整，并说明缺口；不能宣称已充分核验。不具备证据的观点仍可按假设或待验证主张提交，不要求编造材料。
- 保存成功和公开只证明材料可用，不证明其真实或足以支持主张。摘要与摘录不能替代核验必需的原始内容；保留解释摘录所需的上下文。
- 修改材料产生新版本，旧材料、引用和核验结论仍可追溯；旧版本的批准不得自动用于新版本。多个主张可复用同一份材料，无须重复保存相同基线。
- 共享范围受既有会议身份与 DSH 授权约束，不因证据提交自动公开私有 Session 历史、隐藏推理或凭据，也不扩大审核人的执行权限。

每份证据应覆盖以下信息；未知项明确标注未知，不适用项说明原因，不强制不同证据类型提供相同的实验细节。

| 信息 | 要求 |
| --- | --- |
| 标识与版本 | 稳定证据标识、具体版本，更新后保留旧版本。 |
| 标题与类型 | 简短标题及材料类型，如网页、文档、数据、实验、代码或访谈。 |
| 原始来源 | 作者或发布机构、原始 URL 或文件出处；区分原始材料、转载和二手引用。 |
| 时间 | 来源发布日期及采集、观察或实验时间，按类型记录。 |
| 可访问材料与定位 | 共享材料或可访问的固定版本引用，以及页码、段落、表格、代码位置或数据范围。 |
| 观察结果 | 材料记载或实际观察到的结果，与提交者的解释、推断分开。 |
| 获取方法与条件 | 搜集或产生方式；按类型提供样本、步骤、环境和关键参数等核验条件。 |
| 限制与依赖 | 缺失信息、适用范围，以及与其他证据共享的来源或数据；独立性未知时如实标注。 |
| 提交来源 | 提交者的会议身份及提交时间，用于追溯和安排独立审核。 |

材料、主张关联和审核记录分别表达：每次引用说明关联的问题或主张、所用证据版本与具体部分、支持或反驳的理由及推断假设。同一材料对不同主张可以有不同支持程度，不将一项审核结论泛化至所有引用。审核记录另行保留审核人、证据版本与主张、核验时间、实际方式与范围、结论及理由；作者报告的结果不能代填为独立审核通过。

### Code Evidence

代码证据须使审核人能够取得同一版本的相关代码，定位主张，并在需要执行验证时具备复现条件。

- 记录仓库来源和固定 commit；存在未提交修改时保存相对该基线的 diff，包括核验所需的新文件内容。没有 Git 基线时保存可定位的代码快照版本，不能用会变化的分支名或工作目录代替固定版本。
- 提供文件路径、函数或符号及相关位置，行号绑定代码版本。公共区保存代码快照，或关联审核人可访问的固定版本；包含影响判断的调用方、配置及必要依赖，不以孤立片段代表完整路径。相同代码基线可以复用，不要求每次复制整个仓库。
- 主张说明触发条件、预期行为及所指问题；分析说明相关调用路径、条件判断和状态变化，区分源码观察与推断。
- 声称执行过验证时，提供测试或复现脚本、实际命令、环境与依赖版本、输入、预期结果和实际输出，并将该次运行绑定到所验证的代码版本。明确已覆盖及未覆盖路径；未运行时标记静态分析，不写作测试通过。
- 作者运行结果与审核人独立复现分别记录；阅读作者的测试输出不等于独立运行。不能复现或缺少依赖时记录原因及核验边界，不推断通过，也不自动扩大 DSH 权限来执行材料。

### Agenda Direction And Decomposition

- Manager 将复杂目标拆解为可讨论的子议题，为每项明确问题、范围、预期成果、完成条件与前后依赖。
- 有依赖的子议题逐步推进；独立问题可以并行准备，发布仍须符合当前有效议题边界。Manager 可要求补证、继续拆解或推进下一议题，改变用户目标或重大范围须由召集人确认。
- Manager 归纳已公开结论、分歧与证据缺口，不得为了推进流程把关键未解决分歧宣布为已解决。
- Manager 决定接下来讨论什么及其理由；Participant 决定自己的观点和证据。Runtime 保证授权、版本绑定、状态与有序发布。

### Participation And Concurrent Preparation

- 2026-09-14 确认不同 Participant 基于已公开 Transcript 并行协作，不设置逐人发言或全员完成的轮次门槛；正式发布顺序只用于记录和引用。任务授权、完成判断与预算边界以 [Meeting Requirements](./MEETING-ORCHESTRATION-REQUIREMENTS.md) FR-3、FR-4、BR-1～BR-3 为准。
- 不同 Agent 可以并发取证和准备。每个 Agent 同时最多处理一项发言任务；待审稿属于尚未完成的当前任务，不连续堆积新稿。
- Transcript 变化不应触发全员无条件发言。优先向被点名、负责相关问题或需要复核的 Agent 提供相关增量；Agent 完成当前工作后判断是否需要参与下一次贡献。
- 判断依据首先是是否存在自己能推进的待解决问题、证据缺口或路径修订，其次考虑点名和职责分配、新证据及反例。没有新贡献时保持安静，不逐次汇报“不参与”。
- 每次准备绑定所依据的 Transcript 版本，提交说明回应哪些记录及新增贡献。发布前若新增内容实质影响稿件，应退回更新；无关变化不强制全部重做。
- 新证据或异步任务完成也可以触发申请，不必等待 Transcript 再次变化。会议整体以公共内容推进衡量进展，不要求全体 Agent 同步完成同一轮。

### Assignment And Speaking Requests

1. Manager 明确指派的任务不再要求重复申请；Agent 完成后直接提交待审稿，仍须经过边界审核。
2. Agent 主动参与时先提交简短发言申请，说明回应哪条记录或哪个问题、拟补充什么、当前讨论价值及准备状态；新证据申请不强制依赖一条新发布消息。
3. 发言申请属于调度信息，不进入 Transcript，也不形成正式观点、决策或完成事实。
4. Manager 根据当前议题、贡献价值、重复程度及预算决定接受、合并同类申请的安排、暂缓或要求先补证据，并向申请者反馈。合并安排不得替代或改写各 Agent 的观点。
5. 获得安排后 Agent 提交完整待审稿；申请被接受只表示获准准备或提交，不等于内容审核通过。
6. 影响当前决策的关键反例允许紧急申请，但仍不得绕过边界审核直接插入 Transcript。

### Independent Evidence Review

1. 会议设置独立的证据审核员，核查来源能否追溯、证据是否支持所引用的主张，以及适用限制和反例。Manager 负责议题边界与讨论安排，不以边界批准代替证据核验。
2. 普通观点、问题和明确标注的假设不要求逐条核验，通过边界审核即可公开。影响方案取舍、完成判定的关键证据，以及受到质疑的证据，应由 Manager 安排独立核验。
3. 经边界审核的证据可在核验前以“待核验”状态进入 Transcript，供其他 Agent 讨论；不得作为已证实依据使用。待核验不等于待审发言，后者仍不可公开。
4. 审核结论关联所审核的具体证据及其所支持的主张，区分“支持”“部分支持”“不支持”“无法核验”，注明理由、实际验证范围和适用限制。结论不覆盖原文，来源和先后记录保持可追溯。
5. 证据作者不得审核自己的证据。审核员自行提出的新证据同样需要独立核验，不能借审核身份自我认证。
6. 审核员作为固定参会角色接收相关材料，但只在被指派核验或发现关键反例时参与；主动贡献遵循发言申请与边界审核流程，不因固定参会而每轮发言。
7. 证据审核结论不等同于成果完成或决策接受。“部分支持”“无法核验”及未完成核验不得被归纳成全面证实，也不因证据不足删除原有分歧。

## Business Rules

- 发言边界审核与发言人选择是独立职责；无论采用何种发言选择方式，未审内容都不得绕过准入。既有 Manager planning fallback 不构成审核通过。
- 审核通过只表示内容处于讨论边界内，不表示证据可靠、观点成立、成果完成或决策已接受。
- 身份元数据继续用于来源引用、授权和审核独立性；公共观点的价值依据其内容和证据判断。
- 待审提交不能先触发其携带的公开问题、提案、立场或完成声明，再补做审核；发布及其关联公开变化须保持一致。

## Acceptance Criteria

- 提交含证据的观点时，授权审核人能访问所引用版本和具体位置，无须读取作者的私有 Session；待审或退回材料对其他参会者不可见，通过边界审核后方可共享，尚未完成核验时仍标为待核验。
- 仅提供不可访问链接、临时路径或缺少必要上下文的片段时，材料缺口明确可见，不被标为已充分核验；无证据的假设仍可按既有边界提交。
- 同一证据支持两个主张时，分别保留引用位置、推断与审核结论；更新证据后，旧版本仍可访问，旧批准不自动适用于新版本。
- 代码证据能定位固定基线及未提交改动；声称执行测试时，审核人能取得对应脚本、条件和实际输出。仅做静态分析不显示为运行通过，作者运行与审核人独立复现保持可区分。
- 公开论证明确提供主张、证据、推断、反证条件和不确定性；缺证据如实标注，直接观察与假设可区分，单纯填齐字段不等于论证成立。
- 三位 Agent 引用同一篇文章时，会议材料保留一个来源及各自引用关系，不报告为三次独立验证。转载和共同数据依赖在已知时明确记录，未知时不宣称独立。
- 所谓独立验证能指出实际执行过程与观察范围；对同一材料的不同解释不被误计为独立实验证据。
- 从目标能追溯候选路径、关键未知、取证与分析、路径修订及最终方案；仅有发言记录或审核记录不能判定目标完成。
- 阶段成果说明关键选择的证据依据、各部分兼容关系及执行步骤，显式保留假设、风险和影响方案成立的分歧；全员赞同不能替代这些条件。
- Manager 的安排关联求解问题或证据缺口；Participant 的贡献能用于分析、比较或修订路径，Transcript 更新不导致无贡献的自动回应。
- 提交议题观点后、审核前，未获授权处理该提交的 Participant 上下文及正式 Transcript 均不可见该内容；Manager 可以读取该待审版本与适用边界，证据审核员仅按核验授权访问必要材料与主张。
- 对含有权限自述或偏题段落的提交，Manager 能指出具体越界位置及依据；原 Agent 收到反馈，其他参会者不收到被退回正文。
- 修订稿通过后，仅该版本进入正式 Transcript 及后续上下文；旧版本、旧审核或重复请求不能造成误发、重发或提前形成会议事实。
- 对有证据的不同意见、前提质疑和必要背景，不以“与 Manager 意见不同”作为退回理由。
- 审核不可用、超时或重提达到上限时，未审发言不发布，召集人收到明确提示。
- 来源、审核结论和内容版本可追溯；边界批准与事实核验、成果批准保持可区分。
- 复杂议题具有明确拆解和依赖；Manager 能说明为何补证、继续拆解或推进，不越权改变用户目标。
- 两位 Agent 可以并发准备，但同一 Agent 不重复启动发言任务或在待审时堆稿；无关 Transcript 更新不引发全员重做。
- 主动申请被安排后才提交待审稿；明确指派无需重复申请。申请、待审稿和正式发布内容的可见性及效力保持区分。
- 没有新增贡献的 Agent 保持安静；相关新证据可以主动触发申请，紧急反例也经过审核。
- 普通观点和假设不因缺少证据审核被一律阻塞；关键或被质疑证据被安排独立核验，核验前的公开内容明确标为待核验。
- 审核结论能追溯到具体证据和主张，并保留理由及范围；下游引用不把待核验、部分支持或无法核验当作已充分证实。
- 作者不能审核自身证据，包括审核员自己提出的新证据；审核员无须对每次 Transcript 更新都发言。

## Minimal Delivery Scope

2026-09-14，用户确认先交付最小闭环，并要求先制定 RUNBOOK。本节限定首个交付切片，不删除前述目标需求，不代表已授权本轮执行产品代码改动。

### Included

- 固定参会者，Manager 明确指派；每个 Participant 同时最多一项未结束的贡献任务，不同身份可以并行准备和提交。
- 一项贡献关联稿件版本、证据引用及审核结果，不建立彼此独立的申请、稿件、证据核验工作流平台。
- 保存核验材料或可访问的固定版本引用；代码证据关联固定基线、补丁与实际复现材料。用户同日确认：首版保存小型文本材料、代码补丁和固定版本引用；大文件仅记录可访问来源，不直接上传 PDF、截图等二进制文件，不实现分块上传。具体容量限制须进入正式接口，不由执行者猜测。
- Manager 对确切稿件版本做边界审核，退回修改保留旧稿；指定的独立审核员核验关键证据，结果保留具体依据和范围。
- 复用既有正式完成事实与 Captain 接受机制，解除业务推进对 Turn 结束的依赖。必要任务和必要核验未满足时不能正常完成，非阻塞任务不要求全员等待。
- 复用现有身份、repository、outbox、Session adapter 和会议面板，展示任务、待审状态、证据及核验结果，并接通暂停、结束与 Captain 处置。
- Manager 不可用、超时或重提无法收敛时明确等待 Captain，不自动替补或绕过审核。

### Deferred

主动申请、紧急申请、申请合并、自动判断是否参与、自动识别新增消息是否实质影响稿件、自动抓取、来源自动去重、自动执行验证代码、证据变化后的自动关联重审、动态入会、复杂调度评分和自动停滞重规划，均不纳入本切片。

本切片的新贡献任务不接入既有后台 MeetingTask 或私聊 Mailbox；研究和材料提交通过贡献任务完成。旧会议继续保留这些能力及其收尾，不迁移数据。

Manager 在审核时判断上下文变化是否要求重提；材料与审核结论不自动覆盖既有决策，关联关系供 Captain 明确处置。原有能力的保留、停用和存储兼容边界须在实施前逐项确定，不能把“暂缓新增”解释为删除既有用户数据或放宽权限。并行化不允许同一 DSH Session 被并发调用。

### Slice Acceptance

- 至少两位 Participant 同时接受不同研究任务，一位仍在准备时，另一位能提交并经审核发布。
- 审核员能读取被引用的确切证据版本；不能取得材料时记录无法核验，不伪造通过。
- 待审稿不产生公开事实；旧批准不能发布修订稿，重复请求不重发，作者不能自审。
- 必要贡献或核验尚未完成时，Captain 请求正常完成被拒绝；满足既有正式完成条件后，无关任务不阻塞收口，终态后迟到结果不写入。
- 面板可区分准备、待审、退回、等待 Captain 和已发布；会后产出、失败、归档结果及人工介入分别记录。

## Implementation Boundary

现有实现直接提交正式消息并向后续参与者投递；最近的 contentInstruction 改动只提供正文指引，不满足本需求的待审与准入要求。

实施前需同步协议、状态机、持久化、投递和可观察性设计，明确提交与审核标识、版本绑定、边界变更处理、上限取值与召集人处置入口。本文不预设新的工具名、字段名或数值默认值。

并行贡献、基于增量的参与判断和逐条准入取代既有串行 SpeakerAttempt 流程，业务完成不再等待 Turn 结束。已有举手与 Manager planning 能力不代表上述组合行为已实现；协议设计需明确按身份及任务授权、申请处置、任务结束、更新合并、审核与内容发布、预算和停滞检测，以及暂停、结束后的在途工作处置，不能仅修改 Prompt 后宣称完成。

独立证据审核尚未实现。已有 requiredReviewer 对成果的审核不等同于逐证据核验；后续设计需明确证据与主张的关联、核验版本、独立性约束及下游引用状态。审核员需要核验自己提出的新证据时，独立审核人选的安排仍须遵守既有参会授权，不能自动授予新身份或把自审降级为通过。

按求解路径组织公共成果与正式原文追溯的关系尚需接口和设计落实；本文不预设存储形式，也不将现有逐条 transcript 投影视为已满足该目标。

统一论证结构、证据来源关联及独立性记录尚待协议与实现落实；本文确认业务内容与判据，不预设字段编码、来源自动去重算法或新的评分机制。

公共证据区、证据版本及材料访问、主张关联和代码复现材料尚未实现。实施前须形成相应接口与设计，明确材料所有权、授权读取、待审与公开转换、版本保存、访问失败及归档后的材料可用性；不将现有正文链接或 artifact reference 视为上述能力已覆盖。本文不选择物理存储、上传工具、自动抓取或自动运行代码机制。
