# Review Checks

以下是通用检查方法。它们不预设任何业务角色、状态、字段或协议名称；实际约束由证据矩阵中的正式文档条款提供。

## 必经基础检查

对全部 changed hunks 执行：

- 正确性：边界、空值、非法状态、异常转换、异常吞噬和默认值。
- 运行时完整性：并发、生命周期、事务、幂等、资源释放、失败恢复和配置。
- 安全性：输入校验、权限、路径所有权、跨作用域访问、注入、敏感信息和日志。
- 兼容性：已有数据、事件、接口、枚举、配置、exports 和失败语义。
- 架构维护性：领域、runtime、repository、adapter、transport、projection、client 的职责和依赖方向。
- 范围与复杂度：新增机制是否有当前需求、契约、不变量、可复现失败、必要隔离边界或当前消费者作为依据；是否存在覆盖同一触发条件的更小安全改动。

## 必须按 changed surface 触发的检查

- **契约链**：接口字段、类型、schema、序列化、错误和消费者逐层对账。
- **状态链**：文档状态图、命令前置条件、事件、投影和并发交错逐条对账。
- **权限链**：身份来源、授权验证、资源定位、过期/撤销和客户端输入逐条对账。
- **持久化链**：事务边界、幂等记录、副作用顺序、迁移、恢复和部分失败逐条对账。
- **生命周期链**：创建、使用、失败、中断、重试、释放、清理和重启逐条对账。
- **事实链**：正式事实、派生物、归档、缓存、日志和输出之间的单向关系逐条对账。
- **验证链**：需求条款、测试对象、断言、运行时依赖和验证命令逐条对账。
- **复杂度链**：新增抽象、状态、事件、adapter、worker、依赖、兼容层或扩展点逐项连接到当前依据、实际成本和必要 consumer/sink；仅有假设性未来用途时标记为候选 finding。

找不到正式文档条款、真实 validator 或最终 consumer/sink 时，记录为证据缺口或 deferred，不得以经验推断为已满足。

## 模块专项

按 changed files 的实际模块执行专项检查；专项检查只验证模块边界和证据链，不补充业务语义：

- `plugin/src/domain`：纯状态转换和规则是否无隐藏 I/O、外部依赖或未声明默认值。
- `plugin/src/runtime`：应用服务是否是公开命令的唯一入口，副作用顺序和失败语义是否可追踪。
- `plugin/src/repository`：schema、migration、事务、事实、事件和幂等记录是否一致。
- `plugin/src/dsh`：宿主 adapter 是否只实现端口，资源生命周期是否受当前作用域约束。
- `plugin/src/tools` 与 `plugin/src/http`：transport 是否只负责解析、绑定、调用和错误编码，是否存在绕过入口。
- `plugin/src/projection` 与 `plugin/src/client`：是否只消费公开投影，是否把展示状态当成真相或权限依据。
- `plugin/tests`、CI、scripts 和 docs：验证对象是否真实，文档条款、脚本行为和实际运行对象是否一致。

## Findings 门槛

只报告当前 diff 引入、暴露、连通或放大的可操作问题。P0 为严重安全、数据损坏或不可用；P1 为核心错误或高风险回归；P2 为局部真实缺陷；P3 为确实值得修改的结构或验证缺口。纯风格偏好、无依据推测和 diff 外既有问题不报告。

范围与复杂度 finding 还必须同时证明：

1. 当前 diff 引入或实质放大了额外状态、分支、持久化、依赖或维护成本；
2. 该成本没有当前需求、契约、不变量、可复现失败、必要隔离边界或当前消费者支撑；
3. 存在能够保持必要安全、权限、事务、持久化和生命周期边界的更小方案。

单一消费者、单一实现、文件数量、代码行数和个人设计偏好不能单独形成 finding。finding 是否成立与 diff 作者选择的具体修复方案必须分别评价。
