# Test-driven Development

随相关开发任务被动触发。按 [Test Rules](../../../docs/00-governance/TEST-RULES.md) 判断测试的有效性与保留价值，按根 `AGENTS.md` 读取行为依据，按 [Engineering Rules](../../../docs/00-governance/ENGINEERING-RULES.md#validation-and-evidence) 执行验证。

## 确定行为与测试边界

先明确触发条件、预期结果，以及一个违反要求的具体错误。预期来自需求、契约或已确认缺陷，不能仅从当前实现推导，也不能用被检验的逻辑计算 expected。依据冲突且会改变产品行为时，先报告冲突。

检查相关已有测试：能够清楚表达变化时修改或增强，需要独立场景时新增。行为保持的重构优先使用已有测试，有实际保护缺口才补测。

选择能暴露目标错误的简单入口。替身可以控制依赖响应、时间和故障，但不能替代正在验证的逻辑；模拟响应只证明调用方处理，真实依赖协议需要真实组合证据。交互本身属于契约时，可以断言参数、次数和顺序。

例如，契约要求失败后最多尝试三次，可以断言依赖调用次数；内部 helper 被调用几次若不影响契约，就不应冻结。

## 执行红绿循环

对本次任务新增或修改的行为，先写最小必要测试并观察目标失败，再实现行为。接手时已有的实现可以补测，不得先完成本次实现，再以“已有实现”为由跳过测试先行。一个场景可以包含多个互补断言。

1. **运行并解释失败。** 失败应来自目标行为错误或缺失。环境、导入和测试构造错误先解决；新 API 不存在只能说明接口待实现，不能独自证明行为断言有效。
2. **实现并验证通过。** 完成满足场景的最小实现，运行相关测试。失败时区分实现、预期和环境问题；只有预期确有错误或要求改变，才修改断言。
3. **重构并继续。** 通过后简化表达，验证受影响行为，再处理尚未满足的必要场景。

测试直接通过时，检查行为是否已实现、输入是否触发目标、断言是否足够。既有行为确有保护缺口时可保留补充测试；否则复用已有保护，不人为制造 RED。

例如，补测既有的过期请求拒绝行为时，测试直接通过并不说明无价值：核对过期输入确实到达校验，断言检查拒绝结果，且现有用例尚不能识别漏掉该校验的错误。

接手已有实现或补写回归测试时，保留现有工作，需要确认错误识别能力时，在隔离副本运行修复前版本或注入对应生产故障。本次任务若已先写实现，应如实说明偏离，并用上述方式补验，不机械删除现有工作。未观察到的失败如实标明；补验不能描述为遵循了测试先行。characterization 只证明已记录的兼容行为，红绿结果不自动证明预期正确或需求完整。

## 保持测试简单

同形场景可以参数化，保留必要数据行、隔离和每例失败定位。删除重复 setup、无关数据与冗余断言；helper 应降低整体阅读和修改成本。

禁止为测试用例、断言或测试专用设施（fixture、mock/fake、helper、数据生成器、脚本）再编写测试。辅助代码有问题就修正或简化，再运行使用它的生产行为测试；不得移入生产目录规避限制。

## 完成

将必要复现保留为回归测试或吸收到已有 case，清理本次临时 probe、print 和脚本。运行受影响验证，报告结果及证据缺口。

当前要求已有必要保护时停止，不按测试数量或覆盖率继续生成，不自动调用 testcase-review。
