# Convivium Testcase Review

仅由用户显式调用。按 [Test Rules](../../../docs/00-governance/TEST-RULES.md) 判断测试是否有效、值得保留及可以简化，按根 `AGENTS.md` 读取行为依据，按 [Engineering Rules](../../../docs/00-governance/ENGINEERING-RULES.md#validation-and-evidence) 处理验证证据。

## 确定范围

调用方式：`$convivium-testcase-review <范围>`。范围是自然语言线索，可以是路径名、模块名、文件名或函数名，允许模糊名称和通配符，例如 `持久化`、`*checkpoint*`、`plugin/**/*.test.ts`。未给出范围时请用户补充，不默认审查全仓。

由 AI 结合仓库结构、符号定义和引用关系理解范围，不用脚本解析参数，也不要求固定参数语法。使用文件和文本搜索定位候选；通配符作为匹配线索，不作为命令执行。目标为生产代码时，追踪验证其行为的测试，不能只匹配测试文件名。

定位后简要说明实际范围和版本基线；未指定版本时使用当前工作区。维护文件审查清单，区分目标文件与为判断依据、执行路径或保护承接而追踪的必要上下文；范围变化时同步清单。多个候选属于同一目标时一并纳入，存在会改变评审范围的不同解释时再澄清。读取目标测试、所调用的生产代码、测试辅助代码及判断重复所需的相关用例，不自行扩展为全仓审计。

默认只读。用户明确要求结合 PR/module review 时，继承其基线与输出格式。

## 检查单个用例

沿“前置条件和输入 → 实际执行路径 → 断言”核对：

- **依据**：具体预期来自哪里？是否仅照抄当前实现，或用被检验的逻辑计算 expected？characterization 要保持什么兼容行为？
- **识别能力**：哪个具体错误会使测试失败？输入是否触发该错误，断言是否能区分错误结果与正确结果？
- **验证对象**：替身是否提供了本应被验证的结果？模拟数据和故障是否符合场景？交互断言是否对应契约？检查的是项目行为，还是框架机制或无契约意义的实现细节？
- **可靠性**：异步操作是否完成，异常是否吞掉，资源是否清理？独立与成组运行是否受共享状态影响？正常重构是否导致无关失败？

禁止对测试进行测试。发现以测试用例、断言或测试专用设施（fixture、mock/fake、helper、数据生成器、脚本）为被测对象的用例，应报告并建议移除；辅助代码问题通过修正或简化解决，不建议再补一层测试。

缺少依据时标为待核实，不直接判错。需要动态证据时运行相关生产行为测试；必要的故障复现或注入只在隔离副本中进行。区分测试构造失败、错误预期和生产缺陷，不改预期掩盖问题。

## 比较用例集合

区分三种重复：

| 类型 | 判断与处置 |
| --- | --- |
| 代码重复 | 操作和断言同形、仅数据不同，可参数化或共享 setup；保留必要数据行及每例失败定位 |
| 保护重复 | 保留 case 能识别同样的相关错误，且被删部分没有值得保留的定位或反馈优势，才建议删除 |
| 执行重复 | 高成本运行未提供不同边界或新证据，可缩小执行范围、调整层级或复用安全资源 |

同一规则、相同结果或覆盖同一行不能证明重复；不同输入和测试层级可能分别保护不同错误。参数化通常只减少代码，不减少执行次数。合并应列明保留的输入和断言，不把独立场景串成依赖共享状态的大 case。

检查 fixture、helper 和封装能否减少。代码减量本身有价值；比较节省的重复与增加的理解成本，不按 helper 形态或行数单独判断。

例如：

- 空字符串和纯空白名称都应被拒绝，操作与断言同形时可参数化，但保留两行数据；删除空白检查可能只使后一行失败。
- 两个用例以相同条件、入口和断言检查过期拒绝，且没有不同的定位或反馈价值时，可删去一个，指出保留用例如何识别漏掉过期校验的错误。
- 过期请求和无权限请求虽然都被拒绝，却分别保护时效与权限校验，不能因结果相同删除其中一个。

## 衡量成本并决定处置

将所防错误的触发条件、后果和增量证据，与阅读、修改、诊断、运行及不稳定成本比较：

- 重复建库、启动服务、外部调用或固定等待是否必要？
- 数据规模是否用于分页、容量或时序边界，缩小后还会触发目标错误吗？
- 更窄入口或替身能否保留所需证据，是否丢失真实事务、provider 或 Session 生命周期验证？
- 偶发失败来自产品竞态还是测试环境，重试或跳过是否只是隐藏失败？

依据代码可提出减少重复初始化、无关数据或固定等待的建议。声称运行耗时高或替代方案更快时，引用相关运行数据；缺少数据则将性能结论标为待验证，不默认新增基准测试。

据此选择保留、增强、合并、简化、替代或删除。建议合并或删除时，指出原用例保护的具体错误，以及保留用例的输入和断言如何继续识别它；行为已退役或断言无效时说明依据和必要缺口。有独有证据但成本过高时，先比较更轻方案；调整频率或取消须说明证据损失、剩余风险和允许取舍的依据，不能自行降低明确验收要求。

## Finding 分级与收敛

参考 [PR Review 的分级口径](../convivium-pr-review/references/review-checks.md#findings-门槛)，按当前可触发影响分级；下表将其应用到测试资产，审查范围仍遵循本 Skill 的范围约定。优先级表示处置紧迫性，不代表证据置信度。缺少依据的推断进入待核实事项，不降为 P3 来充当已确认问题。

| 等级 | 判断标准与处置 |
| --- | --- |
| P0 | 执行当前测试或清理路径会造成严重安全事件、不可恢复的数据损坏或大范围不可用，有明确执行链路和当前影响证据；立即停止相关执行并修复。不能由被测功能的重要性或假想漏测后果推定 |
| P1 | 核心验收或必需门禁失效，直接掩盖已确认的核心错误或高风险回归，或常见执行路径持续阻断关键验证；应在依赖该证据交付前修复 |
| P2 | 当前合理场景下，测试错误放行违反契约的输入或结果、错误拒绝合法行为，或隔离、异步等待、清理问题使相关验证不可靠；应安排修复。须指出具体错误、输入和断言如何失效 |
| P3 | 不影响已确认核心保护的局部验证可信度、重复代码、冗余自测、无关 fixture 依赖或维护问题，有明确成本和更小替代方式；可低优先级修复。纯风格偏好不报告 |

同类资产问题可能有不同等级：fixture 自测通常属于 P3；若替身直接提供验收结果、让必需的真实边界验证错误通过，应按实际证据损失定为 P2 或 P1。耗时问题需要运行数据，不按 case 数量定级。

输出前按共同根因、触发条件和修复位置合并 findings。同一生产缺陷与直接掩盖它的测试缺口合并报告，说明生产影响与测试证据各自的边界；只有独立触发、独立影响和独立修复边界才拆分。分别核对 finding 是否成立、等级是否准确、处置是否最小，优先增强已有 case，不将一处缺口扩展为假想边界清单。

## 输出与执行

使用中文，沿用 PR review 的 findings-first 风格：先按 P0 → P3 输出已确认问题，再给审查范围、验证缺口和摘要。每项使用可点击文件链接及最小相关行号；工作区审查不要求位置属于 diff。与 PR/module review 组合时继承其输出格式，将下面的保护承接信息纳入对应 finding。

### Findings format

```md
### [P2] 简短、可执行的标题

- 位置：文件链接、最小相关行号及 case/helper 名称。
- 问题：具体错误及共同根因。
- 触发：前置条件、输入、实际执行路径与断言。
- 当前影响：错误放行、错误失败、保护缺失或具体维护成本；区分生产缺陷与测试证据问题。
- 最小处置：增强 / 合并 / 简化 / 替代 / 删除，以及能够消除触发条件的最小改动。
- 保护承接：原本要识别的具体错误；保留哪些 case、输入和断言继续识别它，或明确失去的证据及允许取舍的依据。
- 范围上限：最容易被顺带扩张的相邻能力；无则写“无”。
- 证据：规则、需求、接口、源码或实际命令结果；标明静态论证和动态验证。
```

`最小处置` 定义修复边界，不设计完整实现；`保护承接` 不能只写“已有覆盖”，也不能以全绿或 coverage 不变证明删除安全。

### Final output

Findings 之后按以下结构收口。逐文件列出目标测试、fixture/helper、必要生产代码和依据文档，路径使用可点击链接；可按职责分组，但不得用目录名或“相关文件”代替文件清单。同一文件只计一次，同时属于目标和上下文时归入目标，不要求逐 case 建立台账。

- `reviewed`：已完成与本次问题相关的内容、调用路径或断言审查。只读相关片段时注明章节、符号或行段，不宣称审过整个文件。
- `deferred`：目标文件或必要上下文尚未完成判断，说明具体缺口。仅搜索命中或打开过不等于 reviewed；纯搜索候选经排除后不计入，已声明目标被排除时解释范围调整。
- 分别统计目标文件、必要上下文的 reviewed/deferred 数量；每组 total 必须等于两种状态之和，总计必须等于表中唯一文件数。有 deferred 或目标遗漏时，Coverage 为 incomplete。

```md
## Coverage

- 基线与目标范围：当前工作区或指定版本，以及解析后的路径、模块或符号。

### Reviewed files

| 文件 | 角色 | 状态 | 实际审查内容或缺口 |
| --- | --- | --- | --- |
| 文件链接 | 目标 / 必要上下文 | reviewed / deferred | case、helper、生产符号或文档章节；未完成时说明原因 |

- 目标文件：total N；reviewed N；deferred N。
- 必要上下文：total N；reviewed N；deferred N。
- 总计：唯一文件 N；reviewed N；deferred N。
- Coverage 状态：complete / incomplete。

## Validation gaps

- 实际验证：命令、结果；复用旧证据时注明原基线。
- 未验证与待核实：未运行边界、阻塞原因及影响结论的缺失依据；无则写“无”。
- Validation 状态：verified / partial / not-run / blocked。

## Review summary

- 结论：未发现可行动问题 / 存在需修复问题 / 补齐审查后再决定。
- P0 / P1 / P2 / P3 数量：按收敛后的 findings 统计。
- 最主要风险：当前影响最大的保护缺口或成本；无则写“无”。
```

Coverage 仅表示声明的审查范围是否完成，不表示测试覆盖率或产品需求全部已验证；Validation 独立记录实际执行证据，部分通过但仍有阻塞时写 partial 并列出阻塞项。独立测试审查不输出 PR 合并建议。

范围完成且无 finding 时，开头输出 `No actionable findings.`；没有 confirmed finding 但范围未完成时，输出 `No confirmed findings, but review coverage is incomplete.`。不得把未读或待核实当作没有问题。

用户要求清理时实施范围内修改，对照前后场景和断言，运行受影响验证；完成后报告处置结果、实际验证和残留风险，不把修复前 findings 继续列为未解决问题。
