# Convivium Testcase Review

仅由用户显式调用。按 [Test Rules](../../../docs/00-governance/TEST-RULES.md) 判断测试是否有效、值得保留及可以简化，按根 `AGENTS.md` 读取行为依据，按 [Engineering Rules](../../../docs/00-governance/ENGINEERING-RULES.md#validation-and-evidence) 处理验证证据。

## 确定范围

调用方式：`$convivium-testcase-review <范围>`。范围是自然语言线索，可以是路径名、模块名、文件名或函数名，允许模糊名称和通配符，例如 `持久化`、`*checkpoint*`、`plugin/**/*.test.ts`。未给出范围时请用户补充，不默认审查全仓。

由 AI 结合仓库结构、符号定义和引用关系理解范围，不用脚本解析参数，也不要求固定参数语法。使用文件和文本搜索定位候选；通配符作为匹配线索，不作为命令执行。目标为生产代码时，追踪验证其行为的测试，不能只匹配测试文件名。

定位后简要说明实际范围和版本基线；未指定版本时使用当前工作区。维护文件审查清单，区分目标文件与为判断依据、执行路径或保护承接而追踪的必要上下文；范围变化时同步清单。多个候选属于同一目标时一并纳入，存在会改变评审范围的不同解释时再澄清。读取目标测试、所调用的生产代码、测试辅助代码及判断重复所需的相关用例，不自行扩展为全仓审计。

默认只读。用户明确要求结合 PR/module review 时，继承其基线与输出格式。

范围确定后读取 [审查分级、清单与输出](references/coverage-and-output.md)，按其状态定义建立文件清单与集合比较记录。

## 审查完成条件

本次审查同时回答两个问题：单个用例能否识别目标错误，以及用例集合是否以合理成本提供必要保护。完成前者不能代替后者；找到漏测或完成一次 mutation 验证后，仍须完成集合比较。数量不变可以是合理结果，但不能用“测试都有效”解释全部保留。

先定位同一行为的用例组，再沿下述单例检查与集合比较完成判断。组可以跨文件和测试层级，也包括参数化数据行；按实际入口、输入差异、被保护错误和断言归组，不按文件名或 describe 名称认定边界。只追踪判断该组所需的相邻测试，不扩大成全仓审查。

文件清单与集合比较都完成后才能关闭审查。前轮正确性审查或修复通过的证据可以复用，但不能直接充当本轮已完成精简判断的结论。

## 检查单个用例

沿“前置条件和输入 → 实际执行路径 → 断言”核对：

- **依据**：具体预期来自哪里？是否仅照抄当前实现，或用被检验的逻辑计算 expected？characterization 要保持什么兼容行为？
- **识别能力**：哪个具体错误会使测试失败？输入是否触发该错误，断言是否能区分错误结果与正确结果？
- **验证对象**：替身是否提供了本应被验证的结果？模拟数据和故障是否符合场景？交互断言是否对应契约？检查的是项目行为，还是框架机制或无契约意义的实现细节？
- **可靠性**：异步操作是否完成，异常是否吞掉，资源是否清理？独立与成组运行是否受共享状态影响？正常重构是否导致无关失败？

禁止对测试进行测试。发现以测试用例、断言或测试专用设施（fixture、mock/fake、helper、数据生成器、脚本）为被测对象的用例，应报告并建议移除；辅助代码问题通过修正或简化解决，不建议再补一层测试。

缺少依据时标为待核实，不直接判错。需要动态证据时运行相关生产行为测试；必要的故障复现或注入只在隔离副本中进行。区分测试构造失败、错误预期和生产缺陷，不改预期掩盖问题。

## 比较用例集合

区分三种重复：

| 类型 | 判断与处置 |
| --- | --- |
| 代码重复 | 操作和断言同形、仅数据不同，可参数化或共享 setup；保留必要数据行及每例失败定位 |
| 保护重复 | 保留 case 能识别同样的相关错误，且被删部分没有值得保留的定位或反馈优势，才建议删除 |
| 执行重复 | 高成本运行未提供不同边界或新证据，可缩小执行范围、调整层级或复用安全资源 |

同一规则、相同结果或覆盖同一行不能证明重复；不同输入和测试层级可能分别保护不同错误。参数化通常只减少代码，不减少执行次数。合并应列明保留的输入和断言，不把独立场景串成依赖共享状态的大 case。

对候选重复组做一次删除推演：去掉其中一个 case、参数行、断言或 setup 后，会失去哪个具体错误的识别能力、验证边界或有价值的失败定位？指出承接它的实际输入和断言；没有独有价值且保护已承接时报告精简项，不能只因为原用例有效就保留。

优先比较容易被逐例审查漏掉的组合：

- **参数行只换名称**：检查 fixture 是否真的构造了名称所指的对象或状态。多个不存在的 ID 不自动形成多种实体边界。
- **权限、动作与状态相乘**：检查校验发生在共同入口还是分支内。共享校验可考虑完整规则样本加不同调用形式的代表场景；有实际交互风险或独立入口的组合保留，不能仅凭覆盖同一行删除。
- **单元与组合重复**：核对组合测试是否真正执行了生产编排或真实依赖边界；测试自己循环调用 adapter 再检查次数，不自动增加组合证据。移动独有断言后再判断是否可删除。
- **同一次结果分散验证**：寻找可并入已有 case 的互补断言，保留原有独立场景和失败隔离。

检查 fixture、helper 和封装能否减少。代码减量本身有价值；比较节省的重复与增加的理解成本，不按 helper 形态或行数单独判断。

例如：

- 空字符串和纯空白名称都应被拒绝，操作与断言同形时可参数化，但保留两行数据；删除空白检查可能只使后一行失败。
- 两个用例以相同条件、入口和断言检查过期拒绝，且没有不同的定位或反馈价值时，可删去一个，指出保留用例如何识别漏掉过期校验的错误。
- 过期请求和无权限请求虽然都被拒绝，却分别保护时效与权限校验，不能因结果相同删除其中一个。

## 衡量成本并决定处置

将所防错误的触发条件、后果和增量证据，与阅读、修改、诊断、运行及不稳定成本比较：

- 重复建库、启动服务、外部调用或固定等待是否必要？
- 数据规模是否用于分页、容量或时序边界，缩小后还会触发目标错误吗？
- 更窄入口或替身能否保留所需证据，是否丢失真实事务、provider 或 Session 生命周期验证？
- 偶发失败来自产品竞态还是测试环境，重试或跳过是否只是隐藏失败？

依据代码可提出减少重复初始化、无关数据或固定等待的建议。声称运行耗时高或替代方案更快时，引用相关运行数据；缺少数据则将性能结论标为待验证，不默认新增基准测试。

对发现的保护缺口，先比较增强现有 case、替换较弱 case 和新增 case。一个弱 case 被更强用例替代后，重新检查原用例是否仍有独有价值；不能只追加保护而保留所有旧资产。

据此选择保留、增强、合并、简化、替代或删除。建议合并或删除时，指出原用例保护的具体错误，以及保留用例的输入和断言如何继续识别它；行为已退役或断言无效时说明依据和必要缺口。有独有证据但成本过高时，先比较更轻方案；调整频率或取消须说明证据损失、剩余风险和允许取舍的依据，不能自行降低明确验收要求。

## 收敛与交付

按 [审查分级、清单与输出](references/coverage-and-output.md) 收敛 findings，核对文件清单与集合比较是否闭合，并输出中文 findings、逐文件统计、验证缺口与摘要。未完成的判断必须显式保留为 deferred，不能以零 finding 代替完成审查。

用户要求清理时实施范围内修改，对照前后场景和断言，运行受影响验证；修复后复查受影响用例组的剩余价值，报告新增、删除、替换或仅增强的结果，不以全绿代替精简收口；完成后报告处置结果、实际验证和残留风险，不把修复前 findings 继续列为未解决问题。
