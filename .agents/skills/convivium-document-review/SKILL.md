# Convivium Document Review

让人和 Agent 用最少必要阅读找到有效依据，理解边界并正确行动。以执行效果和维护成本评价文档，不以“符合 AI 口味”、篇幅或固定格式作为质量结论。

## Invocation And Targets

仅在用户显式调用本 Skill 时使用。调用形式为 `$convivium-document-review <目标> [其他目标...]`；目标为路径、文件名、文章标题或以下 Ant 风格模式，可用引号包裹含空格的目标。

| 输入 | 匹配语义 |
| --- | --- |
| 文件路径 | 精确匹配该文件；相对路径以仓库根目录为基准，也接受仓库内绝对路径 |
| 目录路径 | 递归选择该目录内的文档；尾部 `/` 可省略 |
| 无 `/` 的文件名或模式 | 按文件名匹配仓库任意目录，例如 `AGENTS.md`、`*-RULES.md`；同名文件全部纳入 |
| 带 `/` 的模式 | 匹配完整仓库相对路径；`*` 匹配同一路径段内零个或多个字符，`?` 匹配一个字符，独立路径段 `**` 匹配零层或多层目录 |
| 文章标题 | 按 Markdown 文档的首个正文一级标题匹配，不把代码块内文本或小节标题当作文章标题；忽略首尾空白并合并连续空白，其余字符精确匹配 |

先匹配路径、文件名或路径模式；未命中且参数不含 `*`、`?` 时，再尝试文章标题。用户明确说明是标题时直接按标题查找，标题中的 `/` 按普通字符处理。标题命中多个文件时列出候选路径，请用户指定目标，不自动全部纳入；其他无歧义参数可以继续审查。标题未精确命中时可以提供近似候选供选择，但不能自行将近似结果纳入范围。

模式区分大小写，使用 `/` 分隔；只支持上述通配语义，不将参数解释为正则表达式、shell 命令、变量展开、花括号展开或否定模式。多个目标取并集、去重并按路径排序。`docs/**/*.md` 包含 `docs/` 直属文件；`docs/*-RULES.md` 不匹配更深目录。

先用 `rg --files --hidden` 等只读方式建立候选清单，排除 `.git/`、依赖目录和构建产物，再按上述语义匹配；不要直接依赖 shell glob 的展开结果。目录和模式默认选择 Markdown 文档，明确指定的其他文本文件也可审查；被 ignore 的显式路径仍按该路径检查，不因默认清单遗漏而判为不存在。不沿符号链接扩展到仓库外。

开始审查前报告匹配范围和文件数量；目标较多时按目录汇总。缺少参数时请求目标，不从当前讨论或整个仓库推定；零匹配时报告原参数并请求修正，不自动扩大模式。多个参数中只有部分零匹配时指出缺失项，继续审查其余已匹配文件。

示例：

```text
$convivium-document-review docs/30-designs/
$convivium-document-review "docs/**/*-RULES.md"
$convivium-document-review AGENTS.md "docs/40-readiness/*.md"
$convivium-document-review "Engineering Rules"
```

## Scope And Authority

- 审查请求默认只读；用户要求整理或修复时，在已授权范围落实改动，沿用已有授权，不为每一步重复确认。审查请求本身不授权修改、提交或发布。
- 以匹配文件为审查范围；只追踪判断职责、冲突和引用影响所需的直接依据。辅助读取不将被引用文件自动纳入审查或修改范围。
- 读取根 `AGENTS.md` 和 [Document Rules](../../../docs/00-governance/DOCUMENT-RULES.md)，复用已读且未变化的内容。文档分类、优先级、结构和迁移要求以治理文档为准，本 Skill 只提供审查方法。
- 治理审查读取目标规则与相关引用；涉及系统边界或工程方法时补读 Architecture 或 Engineering Rules。产品设计评审按根入口补读需求和契约；核验实现声明时才读取相关源码、测试与 readiness，不将文档审查自动扩为代码审计。
- 触及 RUNBOOK 内容审查或修改时，读取 RUNBOOK Rules 并使用 `convivium-runbook`；本 Skill 仅补充文档职责和引用关系检查，不能替代其决策完备性审查。

## Review Method

先辨认每份目标文档的读者、用途、权威依据和变化频率，再追踪重复或冲突的具体主题。范围较大时可用简表记录归属；不为单文件审查强制创建额外资产。

按目标相关性检查以下维度，无关项不填充模板：

| 维度 | 判断问题 |
| --- | --- |
| 职责归属 | 是否混合规则、需求、方案、当前实现、验证事实与历史讨论？内容是否放在能够独立维护其职责的位置？ |
| 稳定性 | 根入口和长期规则是否夹带阶段状态、版本、源码清单或一次性证据？具体接线和当前状态是否有正确的维护位置？ |
| 唯一依据 | 同一结论是否有多个独立维护的完整版本？摘要是否链接权威来源？看似重复的段落是否实际适用于不同对象或边界？ |
| 读取成本 | 任务能否找到必要规则？读取条件是否过宽、存在循环或多级无效跳转？关键约束是否被长文淹没？ |
| 可执行性 | 适用对象、触发条件、动作与成功判据能否确定？“适当”“完整”“必要”等判断是否有足够依据，还是把关键决策留给执行者猜测？ |
| 行为一致性 | 默认动作、例外、权限和停止条件是否冲突？作者、评审者与机械执行者是否被混用？已有授权是否被错误要求重复确认？ |
| 约束适度 | 是否用必要语义指导工作，还是强迫空章节、重复验证和无关流程？简化是否会移除权限、失败、恢复或数据完整性边界？ |
| 证据边界 | 已确认结论、候选方案、推断、实现和验证是否区分？证据是否有适用基线和未覆盖范围？是否把文档或自动化检查通过写成产品就绪？ |

对可执行性问题，选取目标文档实际服务的一至两个任务场景，沿读取入口走查：能否决定下一步、完成标准，以及相关的例外或停止行为。只做静态走查时明确说明，不声称已经执行真实任务或证明所有模型都能遵循。

## Finding Threshold

- 每个 finding 指向具体文件与最小相关行，说明触发场景、可能的误读或维护后果、依据和最小修正方案。冲突需同时列出两侧位置。
- 篇幅长、文件多、同一词出现多次、标题不同或个人措辞偏好不单独构成缺陷。关键提醒加权威链接可以保留；独立职责即使内容短也可以单独成文。
- 将确定问题、待确认冲突和可选风格建议分开。缺少依据时说明不能判断，不凭更新时间或当前代码自行选择新的产品口径。
- 合并或删除建议必须说明内容去向、需要保留的独有语义和受影响引用；“更简洁”不能单独证明删除合理。

## Apply Authorized Changes

先核对待迁移内容的当前有效性与独有约束，再移入对应权威位置、缩减原文并更新引用。涉及多个文件时保持最终语义一致；完全被吸收的文档才删除，不保留竞争口径或无用途的转发文档。

以治理规则为依据应用上述检查，不把每个审查建议自动提升为仓库强制要求。只有入口或读取路由变化才修改根 `AGENTS.md`；规则变化检查相关 Skill，证据范围变化同步对应 readiness。未决产品结论按 Document Rules 处理，不由整理任务代为决定。

验证遵循 [Engineering Rules](../../../docs/00-governance/ENGINEERING-RULES.md#validation-and-evidence)：检查迁移前后语义保留、受影响链接与锚点、旧引用、相关结构检查和 diff。链接检查复用 Document Rules 的 `python3 .github/scripts/check-doc-links.py` 入口及其覆盖边界，不另写一套检查器。按改动风险选取验证，不因纯文档整理默认运行产品套件，也不为记录一次审查新增 readiness 文件。

## Output

用中文先说明结论及实际范围，再按 P0 → P3 排序给出 findings；可合并相同根因，避免按检查维度凑问题。按有依据的实际后果分级，不因出现 MUST、权限或删除等词就提高等级：

| 等级 | 判断标准 |
| --- | --- |
| P0 | 当前适用的指令会直接导致严重且不可接受的后果，如不可恢复的数据损失或敏感信息泄露；应立即停止使用相关指令并修正。须给出明确执行链路，不能只凭假设风险判定 |
| P1 | 常见任务会被引导越权、违反关键契约、错误交付，或因规则冲突无法继续；应在相关任务继续执行前修正 |
| P2 | 特定但合理的场景会出现误执行、遗漏验证、口径漂移或重复维护，仍有可行替代路径；应安排修正 |
| P3 | 有具体影响但不阻断正确执行的局部可读性、导航或维护问题；可低优先级修正 |

每项采用以下格式，位置使用可点击文件链接和最小相关行号；冲突列出两侧位置：

```text
### [P2] 简明描述问题

- 位置：文件与行号
- 触发与影响：什么任务或条件下，会产生什么后果
- 依据：权威规则、冲突内容或静态场景走查结果
- 建议：消除该问题的最小改动；合并删除时说明内容去向
```

待确认冲突和可选风格建议单列，不强行标为 P3。无确定问题时明确说明，并列出未验证边界。

整理方案说明哪些内容保留、迁移、合并或删除以及理由；用户已要求修复时直接落实有依据的方案。完成后报告实际改动、执行的检查与残留问题，区分静态走查、结构验证和真实任务验证，不给出无证据的“AI 友好度”分数。
