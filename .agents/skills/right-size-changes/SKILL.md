# Right-size Changes

实现满足当前已证实需求的最小完整设计。使用最少必要的概念、状态、接口和依赖，同时满足当前行为、已知失败模式、安全边界、数据完整性和明确兼容性。不要以减少 LOC 代替设计判断。

## 确认范围

从用户请求、验收条件、现有调用方、测试和项目约定中确定：

- 必须实现的可观察行为。
- 必须保持的行为、兼容性和不变量。
- 明确排除的内容。
- 可以复用的现有实现模式。

可安全推断的小歧义不阻塞执行。只有不同答案会改变功能、公共契约或风险边界时才询问用户。诊断请求只报告原因，不自动修复；不要扩大用户授权。

## 新增结构的证据门槛

新增抽象、接口、配置、参数、扩展点、事件、依赖、校验或回退前，指出其当前需求、调用方、可达状态或项目强制边界。无法指出时，不要新增。

优先采用直接、局部、可逆的实现。单一消费者或单一实现通常不需要 registry、factory、strategy 或 provider。抽象不明确时，少量清晰重复优于猜错的通用层。

抽象仅在至少一项当前依据成立时合理：

- 已有多个真实消费者或实现。
- 需要统一执行稳定的业务、安全或数据不变量。
- 能降低当前总复杂度，而非转移复杂度。
- 项目、框架、权限或生命周期边界明确要求。

“第三次再抽象”是启发式，不是硬规则。不要默认套用完整 SOLID；原则名称不能替代当前证据。

## 控制范围

没有当前依据时，不要增加配置开关、feature flag、缓存、队列、并发、批处理、多租户、远程兼容、插件机制、通用框架或额外目录层级。不要顺手重构、重命名或整理无关代码。

遇到“以后可能需要”“为了更灵活”“先预留”“顺便支持”或“完整起见”时，要求对应的当前依据；没有依据就删除该设计。未来想法可以记录为未实现，不要编码成闲置基础设施。

额外工作只有在阻塞当前目标时才能纳入，并限制到解除阻塞所需的最小范围。若会改变产品范围、公共契约或用户选择，先请求确认。

## 保留真实保护

不得以 YAGNI 或 KISS 弱化：

- 外部输入、网络、文件、API 和配置的信任边界验证。
- 身份认证、授权、隔离和 secret 处理。
- 数据完整性、事务、幂等和真实并发控制。
- 明确要求的兼容性、扩展性和技术选择。
- 当前依赖或平台的已知失败模式。
- 合规要求及不可逆、高代价操作的保护。
- 项目既有的架构和生命周期边界。

保护措施也必须对应真实可达风险；不要以“安全”为由堆叠重复校验或无消费者基础设施。

## 验证并停止

运行与改动直接相关的现有验证。新增测试只覆盖新增行为、已知回归风险或必须保持的不变量。重构和删除必须证明行为保持；高风险输出应按风险核对真实结果。

当前验收条件通过、本次变更没有已知缺陷、所有新增结构都有当前依据且未验证边界已说明时，停止。不要继续增加未来能力或整理无关范围。
